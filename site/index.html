The product

A transaction compiler,
not another SDK.

Applications should describe accounts, privileges, and instructions. They should not hand-maintain compiled indices, signature ordering, or byte offsets.

01

Describe

Supply a payer, lifetime value, instruction data, and account requirements. No network or private key is required.

→
02

Compile

Merge privileges, order signers, compile account indices, and encode one canonical transaction model.

→
03

Sign & finalize

Export exact message bytes to a wallet or HSM, attach the returned signatures, verify, then emit binary or base64.

Implemented foundation

One authoritative model from accounts to wire.

The current C builder accepts ergonomic account metadata, promotes duplicate privileges, fixes canonical account order, and emits the same model used by the strict encoder.

  • ✓ Fee payer forced to first writable signer
  • ✓ Duplicate account privileges merged
  • ✓ Program and account indices compiled
  • ✓ Signature count checked before encoding

builder.c 
/* Caller owns storage, blockhash, and signatures. */
solc_transaction_instruction instruction = {
    .program_id = system_program,
    .accounts = transfer_accounts,
    .account_count = 2u,
    .data = {transfer_data, transfer_len},
};

solc_status status = solc_legacy_transaction_build(
    fee_payer,
    recent_blockhash,
    signatures,
    &instruction,
    1u,
    &scratch,
    &transaction,
    &error);

/* Size exactly, encode, then send bytes to a signer. */
solc_transaction_encode(
    &transaction, NULL, 0u, &wire_len, &error);

Why it is trustworthy

Small enough to audit.
Strict enough to reject aliases.

{ }

No ambient authority

No network, clock, randomness, environment, dynamic allocation, or mutable global state in the deterministic C core.

↔

Byte-exact

Every accepted transaction decodes and re-encodes to the exact same bytes. Non-canonical encodings fail closed.

≠

Independently checked

Golden vectors, fuzzing, compiler-determinism checks, and pinned official oracles expose local and upstream drift.

▦

Portable boundary

The protocol truth lives behind a stable C ABI. Rust orchestrates safe I/O and providers without duplicating the parser.

Honest roadmap

What works now.
What becomes the product next.

Available in the kernel today
  • Checked legacy transaction builder
  • Legacy, v0, and v1 strict codecs
  • System, SPL Token, and Compute Budget codecs
  • Exact message-byte extraction
  • Strict Ed25519 verification provider boundary
  • C CLI inspection and round-trip orchestration
Product surface next
  • Versioned transaction-plan schema
  • Compile, attach-signature, and finalize commands
  • Safe Rust builder API over the C kernel
  • Signing bundle with ordered signer manifest
  • Offline v0 lookup-table compilation
  • Consumer-ready CMake and registry packages

Network freshness, current account state, execution, and consensus are separate claims. They will not be smuggled into an offline compiler result.

Distribution strategy

One kernel.
Native packages for each boundary.

Releases begin source-first. Language packages stay thin and carry the same reviewed C implementation rather than translating protocol rules independently.

Primary

C / CMake

solc-wire core

Versioned source archive, installable CMake config, pkg-config metadata, checksums, and an immutable GitHub Release.

After API split

Rust

sys · safe API · CLI

Raw FFI and vendored core, a safe builder library, then a small CLI package. Published only after package dry-runs are reproducible.

After MVP

JavaScript

scoped WASM package

A browser and Node wrapper over the same kernel—never a subprocess adapter presented as a native transaction library.
